## 1. 実測で確定した事実

### 1.1 公式サイトから取れるもの・取れないもの

公式サイト（`https://idolmaster-official.jp/cinderellagirls/vote2026/`）は
Next.js の静的エクスポート。

- **アイドル辞書は取れる。** 投票対象190名の全データがJSチャンク内にJSON配列として
  そのまま埋め込まれている。HTMLのスクレイピングすら不要。
  `slug`（公式のキー名は `idol_code`）、公式表記名、かな、英語表記、属性、
  イメージカラー、公式の並び順IDが揃う。
- **中間発表も得票数も存在しない。** `/system` のスケジュールにはミッション期間・
  引換期間・投票期間の3つしか記載がなく、中間発表の予定はない。アイドル個別ページも
  票数表示のない静的シェル。`api.idolmaster-official.jp` にも公開の集計
  エンドポイントは見つからなかった。**一次情報での代替は不可能。**

### 1.2 報酬の段階閾値（`/achievement`）

| 順位 | 報酬 |
|---|---|
| 1位 | 専用特別衣装＋ブックレット |
| 上位5名 | xRライブ出演＋新規楽曲＋専用衣装 |
| **上位7名** | **新ソロ楽曲＋カバー楽曲＋ソロアルバム「M@STER ARTIST」** |
| 上位15名 | ちびぐるみ |

**順位は連続値ではなく3つの崖。** 8位と9位の差には実質的な価値がない。

### 1.3 佐藤心の歴代実績（`/history`）

| 回 | 順位 |
|---|---|
| 2017 | 9位 |
| 2022 | 8位 |
| 2023 Stage for Cinderella 予選グループB | 1位 |
| 2023 Stage for Cinderella 本選 | 6位 |

3回連続トップ10、ただし5位以内は未到達。**ちょうど7位ボーダーの上。**
→ 追跡すべき問いは「上位10名の順位推移」ではなく **「7位以内に入れるか」**。

### 1.4 公式シェア投稿のテンプレート

```
佐藤心 さんに投票しました！

▼公式サイトで投票しよう！
https://t.co/xxxxxxxx   ← 展開先 /cinderellagirls/vote2026/vote/idol/sato_shin

#シンデレラガール総選挙2026
```

- **名寄せは本当に不要。** 190名の公式表記名は全てユニークで、
  **ある名前が別の名前の部分文字列になるケースもゼロ**（`generate_idols_json.py`
  が毎回この2点を検査し、崩れたらエラーで止まる）。
- スラッグは6名が「姓_名」形式ではなく単一語：
  `anastasia` / `clarice` / `kate` / `natalia` / `helen` / `layla`。
  抽出用の正規表現 `/idol/([a-z_]+)` 自体は問題なく動く。

## 2. Yahoo!リアルタイム検索の実測仕様

LINEヤフーはXの正規データライセンス保有者。ログイン不要・無料。
**`search.yahoo.co.jp` は環境の承認ドメインに追加済み。**

### 2.1 アクセス方法

```
GET https://search.yahoo.co.jp/realtime/search?p={query}&rkf=3
```

クエリは `"{公式表記名} さんに投票しました"`。
HTMLの `<script id="__NEXT_DATA__">` 内のJSONに全データが入っている。
取り出し先は `props.pageProps.pageData`。

| パス | 内容 |
|---|---|
| `timeline.entry[]` | **投稿本体。これを使う。** `id` / `userId` / `screenName` / `createdAt`(unix) / `displayTextBody` / `urls` |
| `timeline.head.totalResultsReturned` | 返却数（実質40が上限） |
| `timeline.head.totalResultsAvailable` | **壊れている。使ってはいけない（§2.2）** |
| `transition.showChart` | ツイート数グラフの有無（常に `false`） |

### 2.2 確定した制約（重要）

190名全員を実測して確定した（2026-08-17 18:34〜18:47 JST）。

- **`totalResultsAvailable` は使ってはいけない。**
  190名の合計が **52,770** に対し、全体クエリ `"さんに投票しました"` は **6,641**。
  8倍矛盾する。実測タイムスタンプから求めた到着率との
  **相関係数は −0.115**（ほぼ無相関、わずかに負）。
  この値で順位を作ると完全に壊れる（横山千佳が1位、佐藤心が89件で下位など）。
- **返却は実質39〜40件が上限。** 190名中176名が39件、13名が40件、1名が32件。
  飽和判定を40件基準にすると39件で頭打ちの個体を取りこぼすため、39を上限とみなす。
  `b` パラメータは**完全に無視される**（`b=200` でも1ページ目が返る）。
  `/realtime/autoscroll`・`/realtime/pagination` はHTMLシェルを返し、
  `/_next/data/{buildId}/...` は404。**深いページは到達不能。**
- **索引の深さ自体は24時間ではなく、最低14日ある。**
  投稿量の少ないアイドルは **340時間前（8/3、投票開始日）** まで届いていた。
  40件がカバーする時間幅の中央値は42.8時間、最短9.6時間（池袋晶葉）、最長340時間。
- **それでも8/3〜の遡及取得は不可能。** 索引が深くても40件上限に阻まれ、
  上位帯のアイドルは16時間程度しか遡れない。
- **`showChart` は全クエリで `false`。** ツイート数グラフは提供されない。
- フレーズ検索の引用符はあってもなくてもほぼ同じ結果（89 vs 90）。

### 2.3 実測できた性質

- **パースは完全に機能する。** サンプル7,416件に対し
  **本文の一致率99.4%、URLスラッグの一致率99.9%。**
  取得できる投稿は本物の公式シェア投稿である。
- **投稿数 ÷ ユニークユーザー数 = 1.192**（190名全体）。
  1.00ではない。同一人物が期間内に複数回投稿している。
- 規模感：到着率の推定合計は **約5,485件/日**。

### 2.5 収集間隔は投稿量の増加とともに短くしなければならない

**これがこの設計の最大の弱点である。**

1回の検索で返るのは39〜40件なので、遡れる時間幅は投稿量に反比例する。
投稿量は投票期間の終盤に向けて増え続けるため、必要な収集間隔は縮み続ける。

実測（8/17〜8/18）:

| 時点 | 全190名の投稿数 | 最多アイドルが39件で遡れる時間 |
|---|---:|---:|
| 8/13 23時 | 39件/h | 十分 |
| 8/16 23時 | 810件/h | — |
| 8/17 20〜22時 | 約500件/h | **3.4時間** |
| 8/17 23時 | 1,088件/h | 約1.3時間と推定 |

投稿量は日を追って倍近いペースで増えている。**4時間間隔では既に欠測が発生しており**、
実際に 8/17 21:55 の収集と 8/18 01:54 の収集の間で、最多のアイドルは 23:04 までしか
遡れず 21:55〜23:04 に穴が空いた。

対処の選択肢:

1. **収集間隔を詰める**（当面は2時間、ピーク帯は1時間）。最も素直だが、
   終盤には1時間でも足りなくなる可能性がある
2. **二段構成**：全190名は4時間おき、上位30名程度だけ1時間おき。
   カバー範囲はアイドルごとに管理しているので、混在させても集計は成立する。
   リクエスト数を抑えつつ、必要なところだけ密に取れる
3. **欠測を許容し、飽和したアイドルの計数を下限値として扱う**。
   ただし影響を受けるのは上位陣＝最も知りたい対象なので、順位付けには使えない

**飽和は `collect_vote_share.py` が警告として記録する。** 警告が出たら間隔を詰めること。
警告を無視すると、投稿の多いアイドルほど実数より少なく集計され、順位が下振れする。

### 2.4 注意

- Yahooのスクレイピングは**Xの規約ではなくYahooの規約**の問題になる。
  グレーである事実は消えない。**アクセス間隔は1.5秒以上空ける**こと。
- サービス仕様の変更で `__NEXT_DATA__` の構造が変わると壊れる。
  パース失敗時は黙って0件にせず、エラーで止めること。

## 3. 設計

### 3.1 却下した案（再提案しないこと）

| 案 | 却下理由 |
|---|---|
| Google Trends | LIVE出演で検索が跳ね、既存人気と交絡して分離不能 |
| X公式API | pay-per-use移行で非現実的（全期間検索はEnterpriseのみ） |
| 自前スクレイピング（twikit / Playwright） | 規約違反＋アカウント凍結リスク |
| キャラ名の名寄せ辞書 | 不要（§1.4） |
| 第三者X APIでの継続収集 | **Yahooで無料で足りるため不要になった** |
| `url:` 演算子での狭域トラッキング（上位10名のみ） | **分析上成立しない（§3.2）** |
| `totalResultsAvailable` を件数として使う | **値が壊れている（§2.2）** |
| 固定ウィンドウでの部分標本サンプリング | **不要。全数が取れる（§3.3）** |

### 3.2 上位10名のみを追う案を却下した理由

技術面以前に分析として成立しない。

- 10名分しか引かないと**総投稿数＝分母が消える**ため、シェアも前日比も出せない
- **圏外から浮上してくる新顔を構造的に検知できない**。7位ボーダーを脅かす相手が
  見えないのは、この追跡の目的そのものを損なう
- 「上位10名が全体の3〜5割」という仮定は誤りだった。実測では上位10名の合計が
  全体の**約12%**しかなく、票が190名に広く分散している
- Yahooは無料なので、そもそもコスト節約の動機がない

**190名全員を引く。**

### 3.3 収集方法と指標

**`totalResultsAvailable` は使わない。投稿本体のタイムスタンプで数える。**

**収集：4時間おきに190名を引く（1日6回・1,140リクエスト/日）。**

- 40件上限があるため、1回で遡れる時間幅は投稿量に反比例する。
  実測で最多の池袋晶葉が40件で9.6時間だったので、**4時間間隔なら
  取りこぼさない**（6時間でも足りるが、終盤の追い込みで投稿量が増えるため
  安全側に取る）。
- 各回の投稿を `post_id` で重複排除して蓄積し、**全190名に共通の固定窓**
  （JST 00:00〜24:00）で集計する。
- **これはサンプリングではなく全数取得になる。** したがって元の要件定義にあった
  「固定ウィンドウで部分標本を取る」設計は不要。
- **飽和の自己監視：** ある回の返却が40件に達したら**取りこぼしの疑い**。
  ログに警告を出し、間隔を詰める判断材料にする。

**指標：**

- **主指標：アイドル別の日次ユニーク投稿者数シェア**
  （その日のユニーク `author_id` 数 ÷ 全190名の合計）。
- **副指標：URL／本文の一致率。** `urls` の展開先から `/idol/([a-z_]+)`、
  本文から `^(.+?)\s*さんに投票しました` を取り、突き合わせる。
  乖離＝投稿前に本文を編集したユーザー。乖離率をデータ品質の警告指標にする。
  実測のベースラインは本文99.4%・URL99.9%。ここから落ちたら異常。
- **累積ユニーク author_id は主指標にしない。** 日次ミッションなので飽和する。

### 3.4 精度の限界（これが最重要）

全数取得になるので二項標本誤差はかからない。残るのは**投稿という確率的な
到着過程そのものの揺れ（ポアソン計数ノイズ）**である。

2つのアイドルのレート差を検出するのに必要な観測日数
（`|λ1-λ2|·D > 1.96·√((λ1+λ2)·D)`、実測レートを使用）：

| 比較 | レート差 | 必要日数 |
|---|---:|---:|
| 池袋晶葉 97 vs 佐藤心 56 | 42% | **0.3日** |
| 神谷奈緒 77 vs 佐藤心 56 | 27% | **1.2日** |
| 佐久間まゆ 69 vs 佐藤心 56 | 19% | **2.8日** |
| 佐藤心 56 vs 依田芳乃 51 | 9% | **16.4日** |
| 佐藤心 56 vs 藤原肇 55 | 1.8% | 426日 |
| 佐藤心 56 vs 緒方智絵里 56 | 0.4% | 10,776日 |

> **レート差20%以上なら1〜3日で分離できる。9%差で約16日。
> 数%差は残り期間をすべて使っても永久に分離できない。**

実測では上位20名がシェア1%前後に密集しているため、**単一の順位は出せない。**
代わりに各アイドルの **取りうる順位の範囲** を出す。自分より有意に多いアイドルの
数から最良順位、有意に少ないアイドルの数から最悪順位を決める。

8/17の9.9時間ぶんのデータでは、佐藤心の取りうる順位は **2位〜52位** だった。
幅が広いのは異常ではなく、観測時間が10時間しかないことの正しい表現である。
日数が積み上がるとこの幅が縮み、それがそのまま進捗の指標になる。

**「帯」という分類は使わない。** 一度実装したが欠陥があった。各帯の先頭とだけ
比較する作りだったため、帯が違っても互いに区別できない組（星輝子24人と
佐藤心22人：差2人・必要13.3人）が生じ、「帯が違う＝差がある」が成立しなかった。

**順位表の形にして偽の精度を出さないことが、この設計で最も重要な判断。**

参考：佐藤心のシェア推定精度（プール日数別）

| プール | 累計投稿数 | 相対SE | シェア |
|---|---:|---:|---:|
| 1日 | 56 | 13.4% | 1.01% ±0.27pp |
| 7日 | 392 | 5.1% | 1.01% ±0.10pp |
| 32日（残り全期間） | 1,792 | 2.4% | 1.01% ±0.05pp |

### 3.5 交絡要因

Google Trends を却下した論理（LIVE出演で跳ねる）は**X共有にも部分的に効く**。
ライブ出演・CD発売・シリアルコード付き商品の発売日には、その陣営の投票行動が跳ねる。
X共有が優れているのは「投票という具体的行動に紐付いているぶん検索ボリュームより
汚染が軽い」という点だけ。

→ **日次系列にイベントカレンダーを重ねて注記する。事後補正はしない。**

課金票は構造的に過小評価される（1万票買った人も共有投稿は1件）。これは補正できない。
ただし「人数1位」と「票数1位」のズレ自体が読み取るべき情報である。

### 3.6 初回実測の暫定結果（2026-08-17 18:34〜18:47 JST）

190名を1回だけ引き、40件サンプルのタイムスタンプから到着率を推定したもの。
**確定値ではない。** 1回の取得ではカバー窓がアイドルごとに9.6〜340時間と
ばらつき、時間帯構成の違うものを比べてしまう（§3.3の4時間おき収集で解消する）。

| 順位 | アイドル | 件/日 | シェア |
|---:|---|---:|---:|
| 1 | 池袋晶葉 | 97 | 1.77% |
| 2 | 一ノ瀬志希 | 96 | 1.75% |
| 3 | 神谷奈緒 | 77 | 1.41% |
| 4 | 佐久間まゆ | 69 | 1.26% |
| 5 | 財前時子 | 60 | 1.10% |
| 6 | 辻野あかり | 59 | 1.07% |
| 7 | 乙倉悠貴 | 59 | 1.07% |
| 8 | 緒方智絵里 | 56 | 1.03% |
| **9** | **佐藤心** | **56** | **1.01%** |

11位以下は北条加蓮・高森藍子・関裕美・本田未央・橘ありす・鷹富士茄子・星輝子・

**ただし §3.4 のとおり、この順序自体はほぼ意味がない。**
1〜4位と5位以下は分離できているが、5〜20位の順序は分離不能な帯である。

### 3.7 日次サマリ（暦日での集計）

4時間おきの速報が直近24時間のローリング窓を見るのに対し、JST の暦日で区切った
集計を1日1回出す。`scripts/daily_report_vote_share.py`。

- **日合計**：対象日（既定は前日）のアイドル別ユニーク投稿者数
- **のべ数**：収集開始日から対象日までの各日のユニーク投稿者数を足し上げたもの。
  同じ人が別の日に投稿すれば別に数える。投票報告は日次ミッションなので、
  のべ数は「延べ何人日ぶんの投票報告があったか」を表す
- 1日ぶんに満たない日は**部分集計**として明示する。収集開始日（8/17）は必ずこれに該当する

**0時のルーティンは集計の前に収集を実行する。** 直前の定期収集は 21:53 なので、
収集なしで集計すると前日の 22〜24時が欠測したまま計上されてしまう。
この時間帯は1日で最も投稿が多いため、欠かすと日合計が大きく歪む。

## 4. 運用

### 4.1 実行の流れ

Claude Codeルーティンが4時間おきに新規セッションで以下を実行する。

```
git checkout claude/cinderella-girl-vote-tracking-qikynt && git pull
python scripts/collect_vote_share.py        # 190名の収集（約7分）
python scripts/rank_vote_share.py           # 共通窓で集計
git commit && git push                      # ← Discord投稿より先に行う
python scripts/post_vote_share_to_discord.py  # 上位15名をDiscordへ
```

**コミットはDiscord投稿より先に行うこと。** ルーティンのセッションは毎回
破棄されるため、データをリポジトリに残さないと蓄積されない。当初は投稿を先に
していたが、投稿が失敗した回の収集データがまるごと失われたため順序を入れ替えた。

### 4.2 環境の前提

環境の承認ドメインに以下の2つが必要。どちらかが欠けると該当の手順で
プロキシに 403 CONNECT で拒否される。

| ドメイン | 用途 |
|---|---|
| `search.yahoo.co.jp` | 収集 |
| `discord.com` | 投稿 |

環境変数の追加・変更は**新規セッションからしか見えない**。ルーティンは毎回
新規セッションで動くため問題ないが、対話セッションで検証する場合は注意する。

### 4.3 秘密情報

ウェブフックURLは環境変数 `DISCORD_WEBHOOK_URL` から読む。
**リポジトリには絶対に書かない**（公開リポジトリのため、漏れると誰でも
そのチャンネルに投稿できるようになる）。値をログや報告にも出さないこと。

### 4.4 運用上の注意

- **収集条件は途中で変えない。** 変えた場合はその日を境界としてデータに記録する
- **返却40件の警告が多数出たら間隔を詰める**（取りこぼしの兆候）
- リクエスト間隔は1.5秒より短くしない
- 収集データは1日あたり約1.5MB。期間を通して約46MB

## 5. 残るリスク

- **`totalResultsAvailable` は壊れている（§2.2）。** 実装で誤って使わないこと。
- **8/3〜8/16は欠測。** 全期間の30%。トレンドの起点が8/17以降になる。
- **順位は出せない（§3.4）。** 出せるのは帯の分類。ここを踏み越えないこと。
- **サービス仕様の変更・終了リスク。** `__NEXT_DATA__` の構造が変わると壊れる。
  パース失敗時は黙って0件にせず、エラーで止めること。
- **正解データが存在しない。** 検証は最終結果が出る9/18以降にしかできない。
- **公開すること自体が観測対象に影響する。** バンドワゴン効果や危機感による動員を
  引き起こし得る。公開範囲は先に決める。

## 6. 出力時の明記事項

集計結果は公式シェア投稿から推定した**投票人数の代理指標**であり、
**公式の投票結果でも得票数でもない**。この旨を出力に必ず明記する。
収集対象は公開投稿のみとし、個々のユーザーの特定・プロファイリングには用いない。
